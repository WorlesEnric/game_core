# Game Core Protocol 1.0

Status: **normative design candidate**, 2026-09-25. Implementation and executable conformance are pending. This document replaces the old protocol; it does not preserve its combat stages or opt-in default. The final instruction in the supplied request establishes English as the documentation language.

## 1. Authority and interpretation

`MUST`, `MUST NOT`, and `SHALL` are requirements. Each `P-nnn` anchor identifies one requirement, including its paragraphs and tables. The operation catalogue in §10 specifies procedures under these requirements. Other documents explain mappings and examples; they cannot change these semantics. A protocol change updates this document, its tests, and the [traceability registry](traceability.json) together.

### P-001
**Genre independence and boundaries.** The kernel MUST provide composition, identity, assembly, execution coordination, lifecycle, and observation contracts without requiring an actor, action, turn, combat, physics, animation, resource, or reward schema. A scope tree, installation dependency graph, execution graph, ECS entity graph, Transform hierarchy, and network topology are separate structures. No one-to-one mapping between plugins, scopes, and entities is required. A plugin MAY introduce any of those domain concepts through registered contracts. V1 executes only trusted, precompiled plugins in one process; isolation means composition visibility, not a security sandbox.

### P-002
**Participants and authority.** `WorldHost` is the sole authority for world lifecycle, command admission, composition revision order, and assembly publication. `CompositionHost` maintains the desired scope/install graph on its serialized control lane. `AssemblyPlanner` is a pure consumer of immutable snapshots; `AssemblyPublisher` applies a validated plan at a safe boundary. `PluginInstance` proposes declarations and owns managed leases, never arbitrary writes to a live ECS world. `StateOwner` is a registered logical authority whose systems write declared state. `ExecutionDriver` runs the compiled execution graph. `EngineAdapter` admits observations and presents committed output. `Observer` reads snapshots/provenance. These are roles, not a requirement for eight runtime objects or interfaces. Within a world, publication and step execution MUST NOT overlap.

### P-003
**Three distinct kinds of change.** `ManagedResourceEffect` acquires/releases subscriptions, service registrations, asset leases, or system registrations; it has a lifetime and cleanup. `CapabilityContribution` is a declarative input to derived bindings, configuration, component requirements, and policies; it has provenance and retraction. `GameplayEffect` is plugin-defined authoritative state change (for example drawing a card or opening a gate); it follows the owner's commit policy. The kernel MUST NOT expose a common reversible `Effect` API implying that these have the same semantics. Retracting a contribution or disposing a resource does not undo committed gameplay.

## 2. Identity, versions, and references

### P-004
**Stable identities.** `WorldId` is a fresh 128-bit session ID, never reused, including on checkpoint restore. `WorldDefinitionId`, `ScopeId`, `TargetId`, `PluginTypeId`, `PluginInstanceId`, `CapabilityId`, `SchemaId`, `OwnerId`, `StageId`, and `DefinitionId` are stable 128-bit IDs with a catalog name for diagnostics. Names use reverse-domain namespaces and are not runtime identity. One world rejects duplicate live stable IDs in a category. Installation keys and target spawn keys are explicitly stored in content/checkpoints/replay records; ordering MUST NOT depend on creation thread or a randomly regenerated installation key. A target is an assembly recipient represented by one primary ECS entity in this backend; auxiliary entities are recipe-owned and need no extra scopes.

### P-005
**Runtime handles.** `TargetHandle` contains `WorldId`, slot, and generation. `ScopeHandle` adds a scope generation; `PluginHandle` adds an installation generation. Installation generation changes on unmount/remount, not ordinary reconfigure, suspend/resume, or in-place package replacement; these change `ActivationEpoch`. Every dereference MUST validate world, generation, liveness, and expected category, plus activation epoch when execution authority is required. Destroy/recreate invalidates handles even when a stable ID is restored. Generations and epochs use unsigned 64-bit counters; overflow rejects further allocation/reconfiguration and requires world recreation, never wraparound. Runtime handles, Unity `Entity`, pointers, and native container views MUST NOT be persisted.

### P-006
**Version domains.** `CompositionRevision` increments only when a composition proposal publishes; it orders scope, membership, mode, configuration, and installation changes. `AssemblyEpoch` increments at the same publication, including lifecycle changes that do not alter component structure. `ActivationEpoch` changes whenever an installation loses or gains execution authority, rebinds, or reconfigures. `SchemaVersion` and `DefinitionRevision` describe content compatibility, not liveness. `LogicalStepId` increments only at successful simulation commit. A publication never increments a step. A `SnapshotToken = (WorldId, AssemblyEpoch, LogicalStepId)` identifies one committed observation image. A no-op proposal returns `NoChange` without increments.

### P-007
**References and leases.** Persistent references use stable ID plus required schema/version or definition revision. Runtime service bindings contain contract ID, provider ID, activation epoch, and a lease; resolve once per assembly, not per target per frame. An async work token contains `WorldId`, installation generation, activation epoch, and operation ID. Stale completion can release its own resources but MUST NOT publish state or reacquire execution authority. Read leases pin immutable snapshots, not live writable components; bounded retention rejects new leases with `SnapshotBackpressure` rather than overwriting leased memory.

### P-008
**Stable ordering and determinism boundary.** Comparisons use canonical big-endian stable-ID bytes, ordinal identifiers, and explicit numeric keys. Registration timing, dictionary enumeration, chunk order, worker index, and ECB insertion timing MUST NOT decide precedence or semantic arbitration. Repeatability is required for pure integer/fixed-rule fixtures given identical build/catalog, composition, ordered admitted input, seed streams, and recorded engine observations. This is not cross-platform floating-point, physics, external I/O, or network lockstep determinism.

## 3. Manifests, scopes, services, and modes

### P-009
**Manifest.** A `PluginManifest` MUST declare protocol major/minor range, exact package/content revision, stable type and installation IDs, required/optional services and versions, service exports, capability rules and contracts, state slots and owners, execution stages, access sets, buffer contracts, resource factories, generated registration keys, and per-slot lifecycle/migration policies. An empty category is explicit. Assets/configuration are immutable validated definitions. The catalog rejects duplicate IDs, unknown schema/contract versions, missing precompiled factories, unsupported required protocol features, undeclared access, or missing policies before activation. Absence of a currently active compatible service provider for a known contract is a runtime dependency wait under P-012, not an unknown-catalog-version error. Dynamic player mounting selects catalog entries; it does not load new CLR code.

### P-010
**Scope membership.** Scopes form one rooted acyclic tree per world. A live target has exactly one `OwnerScopeId`; many targets can share it. A plugin is installed at one scope; a scope may have many installations. Descendant selection includes targets in the provider's own scope by default (`SelfAndDescendants`); `DescendantsOnly` is an explicit selector. Scope membership and parent changes are composition operations, never a side effect of moving a Transform. Removing a nonempty scope requires an explicit `ReparentTo` destination or `DestroySubtree` disposition with all affected targets and installations included in the plan. Cross-world reparenting is invalid.

### P-011
**Service visibility.** Service resolution is identical in both modes. A consumer declares each service dependency. A provider is private to its scope unless `ExportToDescendants` is set; world services are explicitly imported by manifest. A service-isolation boundary blocks ancestor providers for named contracts. The nearest visible provider wins only if its manifest explicitly declares `OverrideAncestor`; otherwise multiple visible single-binding providers are `ServiceConflict`. Same-scope duplicate single bindings always conflict. A `MultiBinding` contract returns all visible providers in its registered stable order. Explicit provider selection is allowed inside the visibility boundary; sibling search and reflection fallback are forbidden. Optional absence becomes a declared `None`/fallback. Required dependency cycles reject the proposal.

### P-012
**Dependency closure.** Required service providers prepare before consumers and retire after consumers. Loss of a required provider automatically makes affected consumers `WaitingForDependencies` and retracts their active contributions in the same plan; optional bindings rebind to their declared fallback. Consumers resume automatically when valid dependencies return. A policy or migration failure in that closure rejects the entire proposal, retaining the old provider and old active assembly. An existing provider that fails unexpectedly cannot be kept active: the world stops admission and faults if a safe dependency-closure deactivation cannot publish. There is no invisible partial success or timeout-based unsafe release.

### P-013
**Mode semantics.** `PropagationMode` is one world-level setting: `Automatic` (default) or `Conservative`. In Automatic, every rule with `PropagationReach = Descendants` applies to all eligible targets within its scope domain, including future targets, without target imports. Rules marked `LocalOnly` never propagate. In Conservative, such a descendant rule applies only if either (a) it has `ExportToDescendants` and the target's recipe/schema/scope explicitly imports its capability, or (b) the target has a full explicit `TargetOptIn` naming the provider installation and capability. This mode gate also applies to same-scope targets selected by a Descendants rule's `SelfAndDescendants` selector. Opt-in is not permission to bypass eligibility, isolation, exclusions, ownership, or conflicts. LocalOnly rules apply at their installation scope in both modes. Imports/opt-ins are data and remain stored when inactive; Automatic MUST NOT manufacture or persist them. Mode changes do not alter services, scheduling safety, or gameplay rules.

### P-014
**Mode transition.** Switching mode is an ordinary atomic composition proposal against an expected revision. Recompute all affected inherited contributions, bindings, state dispositions, and execution dependencies. A conflict, missing migration, or exceeded budget rejects the switch and keeps the old mode/assembly. A successful switch changes mode and derived assembly at the same publication; future descendants follow it immediately. A mode switch is not an invitation to request per-object confirmation. A host may explicitly submit a larger configured budget and retry; elapsed time never approves it.

## 4. Capability derivation and composition

### P-015
**Eligibility.** Targets advertise immutable, reusable compatibility descriptors from type schemas, prefab/template recipes, asset adapters, tags, and explicit declarations. Each rule specifies accepted contract/schema versions, scope reach, and predicates over declared descriptor fields or lower-stratum capabilities. Eligibility cannot depend on arbitrary live mutable ECS values, wall time, or callbacks with side effects. A gameplay state change can enqueue an explicit descriptor update for a later publication. Instance declarations are supported but MUST NOT be necessary for ordinary Automatic descendants of a compatible recipe. Unrecognized targets remain unchanged and get an `Ineligible` explanation, not a guessed adapter.

### P-016
**Isolation and exclusions.** Each scope has independent named `ServiceIsolation` and `CapabilityIsolation` sets; `*` means all contracts. A capability boundary blocks outside rules on the boundary scope and its descendants; providers installed at/below it still work. Exclusions can target a capability, rule, or provider on one target or scope subtree. Denial along the propagation path wins over imports, opt-ins, and selection overrides in both modes. A descendant cannot reopen an ancestor boundary; the host must edit that boundary. Sibling branches do not inherit each other's providers. These semantics support expressiveness without confusing service access with derivation.

### P-017
**Contribution identity and ownership.** Each candidate has `ContributionId = (PluginInstanceId, RuleId, TargetId, CapabilityId, OutputSlot)`, immutable payload revision, and provenance. Its identity survives configuration changes; removed/recreated installations get a new generation. A catalog `CapabilityContract` declares output slots, schema, composition policy, and reducer version. All candidates for a target/slot are composed before assembly. Support from multiple contributions is a set of IDs, not a boolean owned by the last plugin. A plugin cannot remove another plugin's contribution or components it does not own.

### P-018
**Precedence.** Eligible candidates sort by higher signed `Priority`, then nearer provider scope (greater depth), then ascending `PluginInstanceId`, `RuleId`, and `OutputSlot` bytes. Priorities are bounded 32-bit manifest values. This total rank orders declared replacement/reduction choices; it does not silently resolve exclusive or incompatible conflicts. Explicit target/scope overrides are versioned composition data: `SelectProvider` names an eligible candidate and is legal only for `Replace` or `Exclusive`; missing selection rejects the plan rather than falling back. Explanations include losing candidates and rank components. Neither node insertion order nor worker timing participates.

### P-019
**Composition policies.** Every output slot MUST choose exactly one policy below. Mixed policies for the same contract/slot are catalog errors. A reducer is pure, bounded, versioned, and supplied by that contract's package; the kernel does not infer numerical semantics.

| Policy | Effective value | Failure/override behavior |
|---|---|---|
| `Additive` | All unique contributions folded in precedence order by declared reducer, or canonical set union. | Reducer validates overflow/range; error rejects whole proposal. No assumption that arbitrary addition is associative. |
| `Replace` | Highest-ranked candidate, unless valid `SelectProvider` overrides it. | Lower-ranked candidates remain candidate provenance, not active support for the selected output. Choosing by rank is an explicit contract choice. |
| `Ordered` | All candidates topologically sorted by declared before/after keys, with precedence as ready-set tie breaker. | Unknown required key/cycle rejects; optional key edges apply only when endpoint exists. |
| `Exclusive` | Exactly zero or one candidate, or the explicitly selected eligible winner. | More than one without selection rejects, even if ranks differ. Losing providers remain inspectable. |
| `Incompatible` | Cross-capability incompatibility sets contain at most one active member. | Reject conflict; remove/exclude one in the same proposal. Priority cannot destroy an incompatible capability. |

### P-020
**Configuration and overrides.** Contract fields explicitly use scalar replacement, canonical set union, or a registered bounded reducer; arrays are ordered values unless specified otherwise. Schema defaults, inherited contributions, and local configuration patches are separate provenance layers, in that order. A local patch has an explicit mask of fields; null/missing are distinct. Reconfiguration changes effective configuration only. It MUST NOT reset mutable state or rewrite committed history except through an explicit registered migration/reset disposition. No generic deep merge is permitted.

### P-021
**Termination.** The catalog assigns capability contracts strata `0..31`. A rule may read static descriptors and capabilities in strictly lower strata only; outputs occupy its declared stratum. Negative tests are allowed only on finalized lower strata. Rules cannot create targets, scopes, plugins, rules, or live gameplay effects during derivation. One rule emits at most the manifest's fixed bounded output slots per target; recursive terms/new IDs derived from prior output are forbidden. Each stratum executes once over canonical candidates; there is no unbounded fixed-point loop. Composition within a stratum cannot feed eligibility in the same stratum. A dependency violating these rules is a catalog error, even if a sample happens to converge.

### P-022
**Budgets.** `PropagationBudget` limits examined candidates, emitted contributions, affected targets, temporary bytes, wall-clock preparation deadline, and safe-point apply cost estimate. The default reference limits are 1,000,000 candidates, 250,000 contributions, 100,000 targets, 128 MiB temporary storage, 2 s preparation, and 8 ms estimated application; these are provisional guardrails, not product capacity claims. Planning can yield between bounded batches while the old epoch continues. Exceeding any hard count/memory/deadline yields `BudgetExceeded` with top fan-out causes; no partial propagation publishes. An apply-time overrun emits a metric but cannot safely abort halfway: finish or fault. A caller may configure a larger limit, schedule a paused-world publication, or split independent changes explicitly. The kernel never silently truncates eligible descendants.

### P-023
**Incrementality.** The implementation MUST index scope ancestry/membership, descriptor-to-target matches, provider/rule-to-contributions, capability reverse dependencies, service consumers, and state-slot support. An edit invalidates its dependency closure; derivation examines indexed candidates and changed paths, not the entire tree on every logical/render step. A world mode switch can invalidate the world. New targets, descriptor changes, boundary edits, service changes, and moves all enter the same invalidation process. An independent full recomputation oracle MUST match the incremental effective assembly/provenance for randomized operation sequences. The indexes are derived data and rebuildable, not a second source of authoritative gameplay state.

### P-024
**Spawn and despawn.** A precompiled `SpawnRecipe` contains base schema/layout, immutable definitions, descriptor, required asset leases, auxiliary entity recipe, and derivation template. Cache derived variants by recipe revision, scope inheritance fingerprint, mode, and catalog hash. On spawn publication, validate against the current composition revision; a stale variant is recomputed or rejected `StalePlan`, never published half-assembled. A target first becomes query-visible with its complete effective assembly and ownership bindings. There is no frame requiring manual descendant wiring. Despawn retracts target contributions, closes its command route, fences users, and destroys only recipe-owned entities/resources. Already committed events keep stable IDs, not dangling handles.

### P-025
**Reparenting and provider change.** A subtree move diffs the union of old and new ancestor rule/service sets, plus descendant overrides and dependency closure. Membership, contributions, bindings, and parent pointers publish together. Unrelated targets retain values and state. Old inherited configuration is removed, new configuration composed, and target-local state is preserved according to its slot policy. Replacing a provider under the same installation identity increments activation epoch and revision; different identities require explicit replacement mapping if state is to transfer. Cross-world movement uses checkpoint/export plus a new world's spawn/restore contract, not this operation.

### P-026
**Explanation.** `Explain(TargetId, CapabilityId, SnapshotToken)` returns matching and rejected rules, source scope path, descriptor evidence, exclusions/boundaries, mode gate, stratum, candidates, composition decisions, support IDs, resulting recipe hash, and state disposition. Records may be interned/compacted but remain reconstructable for the retained epoch. Diagnostics report affected counts and invalidation reasons without retaining an unbounded full string tree per entity. `CompositionPublished` and `CompositionRejected` include operation ID, old/new revision, plan hash, counts, and diagnostic keys.

## 5. Assembly, state, and publication

### P-027
**Change plans.** A proposal specifies expected `CompositionRevision`, catalog hash, operation ID, and canonical input hash. `ChangePlan` contains an immutable before/after composition diff, contribution delta, service binding delta, ownership map, compiled execution plan, structural operations, state dispositions, resource acquisitions/releases, invalidation set, budgets, and a content hash. It has states `Draft → Validated → Prepared → Applying → Published`; alternatives are `Rejected`, `Cancelled`, or `Faulted`. Only one plan per world may enter `Applying`; concurrent proposals serialize by host admission sequence, never merge accidentally. Plan preparation can overlap simulation because it does not read live mutable state.

### P-028
**Validation.** Before preparation, validate catalog/version compatibility, acyclic scope/service/stage graphs, eligibility/strata, conflicts, support/removal policies, generated factories, asset availability contracts, state ownership, buffer producer/consumer contracts, budgets, and expected revision. Validation is exhaustive enough to report related diagnostics, but does not guarantee allocations or native operations cannot fail later. At application, recheck revision, world/lifecycle state, resource readiness, and state-dependent migration preconditions. Stale plans reject without mutation; a host may regenerate with a new operation ID and new expected revision.

### P-029
**Preparation.** Allocate unpublished bindings, immutable blob/config tables, inert system instances where possible, resource leases, and migration storage. Registrations/subscriptions acquired here MUST remain gated and cannot emit gameplay commands until publication. The world may keep running its old assembly. After admission closes and jobs drain, copy only state slots needed for migration into bounded scratch storage; run pure fallible migrations there before the first live write. A preparation/migration failure releases staged leases in reverse dependency order and leaves the old assembly intact. Public callbacks with irreversible side effects are not allowed as preparation actions.

### P-030
**Publication.** At an end-of-step or idle boundary: close step and command admission temporarily; drain all old world jobs and adapter readers; revalidate; stage migrations; apply structural/state changes; install new binding tables and execution graph; preinstall/validate new ingress gates closed; construct the complete observation image and result record. Then a nonthrowing serialized commit switches the published revision/epoch/mode/image and active gate table together and reopens admission. Gate checks derive authority from that committed table; no fallible plugin callback is allowed in the pointer-switch operation. No observer or system sees a mixture of old/new assembly. Delivery of postcommit notifications is separate and its failure cannot unpublish an epoch. Only this boundary uses a world-wide fence for composition; normal stages use dependencies. Failed/no-op publication cannot emit `CompositionPublished`. For CommandDriven idle worlds, this boundary needs no empty simulation step.

### P-031
**Apply failure.** The visibility guarantee in P-030 is not storage rollback. If anything fails after the first live write (including ECB playback, allocation, native API, or activation gate installation), the world enters `Faulted`, admission remains closed, no epoch or new snapshot is published, and no simulation resumes. Its last committed immutable snapshot is inspectable but its live ECS storage is unavailable except to controlled teardown/recovery. V1 does not implement a universal undo journal; recovery recreates a world from a checkpoint or initial definitions. An external gameplay side effect cannot be erased by this procedure. A partially applied plan is never retried against the same live storage.

### P-032
**State dispositions.** Every state slot identifies `(TargetId, OwnerId, SlotId)`, schema/version, initialization policy, configuration-update policy, owner-transfer policy, and last-support-loss policy. Existing state defaults to `Preserve` when the owner/schema stays compatible; a missing compatible policy is a validation error, not implicit zero initialization. A version change uses a registered `Migrate` function; `Reset` requires an explicit manifest-supported proposal field and reason. Last-support loss MUST declare one of: `RemoveDerived` (only disposable derived data), `PreserveDormant` (persistent state stays in ECS, has no active writer/executor, is excluded from active queries, and is serialized), or `TransferTo` a named available owner with a migration. Dormancy is an explicit observable state, not silently runnable orphaned data. Reacquiring the same slot resumes its data; destruction of its target deletes it. A reset/removal never reverses external events.

### P-033
**Shared support and component lifetime.** Derived component existence is governed by the union of effective support sets and the slot policy. Removing one provider removes exactly its support; final removal is allowed only if no other capability/recipe requires the component. Base recipe components are not owned by propagated providers. Where one ECS component implements several slots, the generated layout declares a single physical owner and a field mapping, or splits storage; competing arbitrary component initializers are rejected. Runtime state is not recomputed from defaults on every assembly diff.

### P-034
**State authority.** Each authoritative state domain has one `OwnerId`; its registered systems may write only their declared slots/components and partitions. Multiple systems under that owner need dependency order or provably disjoint generated partitions. V1 accepts disjointness only from validated, mutually exclusive `PartitionId` assignments, not arbitrary query-predicate claims. Overlapping writers from different owners reject assembly unless ownership is explicitly transferred. DI services expose read snapshots and commands, not independent mutable mirrors of ECS state. An engine-owned physical domain is declared as external authority; its ECS data is stamped observation, and ECS submits intent through that adapter.

## 6. Temporal and execution protocol

### P-035
**World lifecycle.** A world is `Created → Running ↔ Paused → Stopping → Disposed`, with `Faulted` reachable from any nonterminal state and recoverable only through recreation. Created worlds become Running only after an initial validated assembly publication. O-26 pauses/resumes at a committed boundary. Paused worlds accept bounded queued commands and composition proposals but do not advance simulation; composition may publish snapshots. Pause/resume changes the separately queried host lifecycle status, not AssemblyEpoch or LogicalStepId. World identity scopes handles, commands, jobs, services, event cursors, and resources. World disposal is not scene unload; scene adapters explicitly request the applicable operations.

### P-036
**Temporal models.** A world chooses `FixedStep` or `CommandDriven` at creation; changing it requires checkpoint/recreation in V1. FixedStep configuration declares positive step duration, scaled/unscaled host clock source, and catch-up limit. The host accumulates elapsed time and admits at most the limit per pump, retaining remaining debt and emitting `TimeDebt`; it never silently increases step duration or discards debt. Pause freezes simulation accumulation. CommandDriven advances only for accepted commands or explicit registered `WakeRequest`s; no inputs/wakes means zero logical steps. Rendering, host callbacks, resource cleanup, and composition processing may continue independently. No kernel rate, turn, or physics phase is prescribed.

### P-037
**Step admission.** An input cutoff seals each step's batch with a monotonic host-assigned admission sequence. CommandDriven admits one pending command or one wake per logical step by default; a domain can declare an atomic batch envelope as one command. FixedStep consumes the sealed prefix up to its configured capacity and retains the remainder. Commands arriving after cutoff wait for the next step. Duplicate request keys return their recorded result, not another execution. A domain rejection still commits an observable rejected command result in a logical step. Composition publishes before the next input seal; queued inputs are revalidated against current bindings, schema, authority, and target liveness, without retaining stale component pointers. Terminally invalid inputs finish as `Rejected` without an empty CommandDriven step.

### P-038
**Clocks.** `LogicalStepId`, fixed-step simulation duration, monotonic host timestamps, and plugin-local clocks are distinct. CommandDriven has no implicit elapsed simulation seconds; its commands can explicitly advance domain time. A plugin local clock registers how it advances, pauses, and persists and can schedule a typed wake; ordinary wall-clock reads are unavailable inside repeatable rule functions. Wake sources have finite queue/budget and explicit clock type. Pausing cancels/defers wakes according to the declared clock policy; no timer callback mutates ECS directly.

### P-039
**Stage registration.** A stage declares namespaced `StageId`, version, owner package, system factory keys, activation membership, `Before`/`After` dependencies (required or optional), read/write sets, buffer ports, and host affinity (`ManagedMain`, `BurstJob`, or adapter main thread). Each system entry also declares its own access sets and explicit system-key dependencies within its stage. Shared stage declarations coalesce only if their contract/version matches; system instances have their own unique keys and declared world/per-partition multiplicity. A world owns at most one system instance per key. Missing required stages/systems fail; optional edges disappear when absent. The kernel's boundaries `BeginStep` and `PublishStep` are synchronization mechanisms and not game phases.

### P-040
**Execution plan.** Compile stage edges, each stage's internal system DAG, buffer producer-before-consumer edges, structural playback boundaries, and explicit owner ordering into a DAG. Stage incoming dependencies precede all its root system entries; its outgoing completion follows all leaves. Both levels and their access sets enter validation and the plan hash. Independent ready nodes are ordered by ascending StageId then system key for trace stability and may execute concurrently. Overlapping read/write accesses require a directed path in that expanded DAG or validated disjoint partitions, including systems coalesced into one stage. A write/write or read/write conflict without a semantic edge is `AmbiguousOrder`; the scheduler MUST NOT invent gameplay order from package load order. Cycles report their edge sources. Multiple independently authored plugins resolve conflicts by declaring compatible stage contracts/edges or using a shared owner request port, not by forcing a universal gameplay coordinator.

### P-041
**Concurrency and structural work.** Within a stage, systems can update owned components directly and schedule jobs. The execution driver tracks all handles, including jobs using native containers not tracked by ECS component safety. Dependencies protect readers/writers and buffer lifetimes; no detached job may retain world memory. Structural operations record into a declared stage-local deferred buffer and play back after its producers finish and before dependent readers. Parallel playback keys use stable target/request order when order is semantically relevant. An ECB/deferred structural buffer is not a gameplay transaction or a reason to route all writes through a global queue.

### P-042
**Commands and requests.** External `CommandEnvelope` carries request key `(WorldId, IssuerId, IssuerSequence)`, target stable IDs, payload schema/revision, expected domain version if needed, and admission result token. The host validates envelope/route/capacity; the state owner validates gameplay. `Request` is a typed transient inter-system message routed to a named owner and consumer step/stage, not a committed fact. Within an active stage, owner-internal computation may use direct writes instead of requests. Cross-owner mutation requires a request or explicit transfer contract. `RequestResult` is `Accepted`, `Rejected`, `Cancelled`, or `Committed` with reason and optional committed event cursor; admission acceptance is not gameplay success.

### P-043
**Buffers and bounded work.** Each buffer contract declares schema, lifetime (`Stage`, `Step`, or bounded `NextStep`), producer keys, exactly one consuming owner, consumption stage, order key, capacity, overflow behavior, and drain/cancel policy. Duplicate producers are legal when registered; fan-out uses explicit immutable read ports. Required gameplay input overflow rejects the affected command/batch before mutation; no silent drop. Diagnostic/presentation buffers may use explicit lossy policies with counters. No consumer reads a buffer before producer completion. Unconsumed step buffers fail commit validation; bounded next-step queues retain stamped stable references and are revalidated after composition changes. Cycles between stages/ports require explicit next-step scheduling. Within its declared stage, a domain owner may use a finite worklist/reaction loop with explicit ordering, reserved capacity, maximum iterations, and prewrite overflow rejection; it cannot dynamically reenter the stage graph. The kernel does not mandate a reaction-wave policy or ban bounded same-step domain computation.

### P-044
**Commit and domain transactions.** A plugin may implement multi-entity atomic decisions by gathering intents, validating all relevant versions/resources, computing a bounded write set, then applying it under its single owner before emitting tentative internal receipts. The kernel does not infer rollback, fairness, economic conservation, combat ordering, or atomicity from ECBs. A successful logical step completes all required work, validates required drains, prepares committed events and a consistent snapshot, then nonthrowingly advances `LogicalStepId` and exposes output together. If unexpected failure follows authoritative writes before that publication, fault the world; do not retry the half-step. Postpublication subscriber-delivery errors do not undo the committed step. A domain may reject a staged command without faulting when it has not applied its write set. No universal speculation, CPU ROB, or global transaction queue is part of V1.

### P-045
**Observation and external output.** Observers see immutable images at `(epoch, step)` publication only; they cannot use inspection to obtain writable ECS references. `CommittedEvent` records stable IDs, schema/revision, step, epoch, event sequence, and causal request. Event cursors and snapshots have configured retention bounds. Internal publication is once per committed operation/step in a live world; subscriber delivery is at-least-once within retention, using `(WorldId, event sequence)` deduplication. Lagging readers receive `CursorExpired` and resynchronize from a snapshot. Irreversible output adapters consume only committed events, use explicit external idempotency keys, and persist an outbox when delivery must survive crashes; ordinary in-memory events make no durable exactly-once guarantee.

## 7. Lifecycle, in-flight work, and recovery

### P-046
**Installation lifecycle.** Installed instances use `Registered`, `WaitingForDependencies`, `Preparing`, `Active`, `Quiescing`, `Suspended`, `Retiring`, `Disposed`, and `Failed`. Mount is declarative registration plus attempted activation; missing required dependencies yields a published waiting instance with no active contributions, not a half-active plugin. Activation requires dependency closure and publication. Explicit suspension stops ingress/execution and retracts active contributions using slot policies while retaining installation/configuration; resume rederives against current ancestry. Replacement/reconfiguration stages a candidate activation while the old Active activation continues; success transitions old activation → Quiescing → Retiring and candidate → Active at one publication, with the installation generation unchanged for an in-place update. Voluntary teardown failure before mutation restores old Active gates; failures after mutation follow P-031. Failed preparation of a new instance is observable and retryable only by an explicit new operation.

### P-047
**In-flight lifetime.** Quiescing closes new managed callbacks/commands from the retiring activation and freezes affected admission. Already executing jobs MUST finish before storage or code-owned resources are released; job cancellation is cooperative intent, not memory reclamation. Accepted but unexecuted commands to a suspended/removed route finish `Cancelled(RouteRetired)` unless the port explicitly declares stable-ID rebinding to a compatible owner. In-flight stage/step execution reaches its commit/fault boundary before composition apply. An async completion with an old epoch is discarded and its staged leases released, even if the stable plugin ID now exists again. Callback gates are checked on dispatch and on completion.

### P-048
**Teardown.** Teardown order is: close ingress; settle current step; fence tracked readers/jobs; retract/publicize the new assembly; retire old resources in reverse dependency order; within an instance dispose leases in reverse acquisition order. Dispose each lease at most once, attempt all independent cleanup, and aggregate failures. Resources still reachable by unfinished work are quarantined and retained; elapsed timeout only reports `TeardownBlocked`, never authorizes free. Retired cleanup failure reports `PublishedWithCleanupErrors` and keeps tracked quarantined resources, not a false `Disposed`. A failing subscription disconnector remains behind a closed epoch gate. World shutdown eventually disposes owned ECS storage only after its users end; a nonterminating native job may require process termination outside this protocol.

### P-049
**Recovery limits.** Pre-mutation failure leaves the old published world usable, with staged resources cleaned or quarantined. Post-mutation/step failure halts simulation, preserving the last good observation image and fault record. Recovery creates a new `WorldId` from a verified checkpoint or initial catalog, validates/rebuilds composition and recipes, restores state, then reopens admission; old callbacks/handles never become valid. No hidden automatic replay of external side effects is allowed. Retryable transient resource failures use host-configured bounded attempts with new operation IDs; correctness failures require changed input/catalog. V1 provides checkpoint recovery, not historical gameplay undo or arbitrary live code replacement.

### P-050
**Cancellation and idempotency.** Every mutating public operation has an `OperationId = (WorldId, IssuerId, IssuerSequence)` and canonical input hash; a command's request key is that same operation identity. First submissions from one issuer use strictly increasing sequences across its control operations and commands; retransmissions may reuse earlier IDs. Create/restore use a caller-reserved fresh WorldId before allocation; the application's bounded host ledger holds this session reservation and operation until the new world owns it, and retains the reservation through failed/cancelled attempts for its process lifetime. Internal suboperations use the parent's operation ID plus a bounded work ordinal. A per-session ledger returns the same pending/terminal result for the same ID/hash; the same retained ID with different input yields `IdempotencyConflict`. The ledger has configured capacity; terminal entries may be explicitly acknowledged/evicted, after which any absent ID at/below the issuer's retained admission high-water mark returns `ResultExpired` and cannot execute, including unseen out-of-order submissions. Issuer high-water marks persist until world disposal; new issuer registration is bounded and old issuer IDs cannot be reused to reset their sequence. Restart creates a new world/session; durable replay safety requires the checkpoint/outbox contract. Cancellation is accepted before `Applying` or command execution admission, cleans staged work, and returns `Cancelled`. At/after that cutoff it returns `TooLate` and the actual operation must be awaited. Retrying a rejected revision requires a new operation ID, never mutating the old request.

### P-051
**Operation discipline.** §10 is the complete V1 kernel operation set. All mutating operations execute on, or enqueue to, the host control lane; plugins submit proposals rather than calling live ECS mutation APIs. Each accepted operation returns a handle immediately, then a terminal result with diagnostic IDs. Status/query methods are pure and cancellable without changing the world. Unsupported operation variants reject before acquisition. A queued cancellation and publication race is resolved by the serialized control lane at the stated cutoff, never by thread timing inside jobs. Failure/cancellation outcomes MUST be observable even when no gameplay step occurs.

### P-052
**Diagnostics.** Errors have a stable code, world/operation/plan identity, phase, involved rule/stage/schema IDs, provenance pointers, counts/budgets, and retry classification. Required codes include `StaleHandle`, `StalePlan`, `MissingDependency`, `ServiceConflict`, `CapabilityConflict`, `AmbiguousOrder`, `Cycle`, `Ineligible`, `UnsupportedVersion`, `OwnershipConflict`, `BudgetExceeded`, `MigrationRequired`, `ResourceUnavailable`, `Cancelled`, `TooLate`, `IdempotencyConflict`, `ResultExpired`, `ApplyFault`, `TeardownBlocked`, and `CursorExpired`. A rejection MUST explain the smallest known conflicting set or a bounded summary with retrieval key. Logging never changes precedence or world state.

## 8. Persistence, evolution, and conformance

### P-053
**Checkpoint.** Checkpoints are taken at a committed boundary after required jobs complete. They contain catalog/protocol fingerprints, world definition/temporal settings, step/time/debt, stable scope/install/target IDs, descriptors, explicit imports/overrides/exclusions, mode, definitions, active and dormant authoritative state, owner versions, RNG streams, bounded pending next-step messages, and external outbox/dedup cursors when used. Raw host timestamps are normalized to declared clock policy. New host commands wait during capture; already queued external commands are either included with ledger/cutoff or explicitly rejected before capture according to the checkpoint option, never ambiguously omitted. Restore validates everything into a new unexposed world before publication.

### P-054
**Serialization.** Wire/save data uses schema IDs, integer versions, explicit field IDs, canonical byte order, length bounds, null semantics, and reference tables; no CLR assembly name or engine handle serves as its identity. Unknown required fields/schema versions reject; explicitly optional presentation fields can be skipped. Generated serializers and registered directed version migrations replace reflection-based type construction. Migration paths must be unique for a requested source/target pair; ambiguity is rejected. Pure definitions/rules can be reused elsewhere; Unity assets, Entity layouts, Jobs graphs, physics observations, and presentation semantics require engine-specific conversion/reimplementation.

### P-055
**Protocol evolution.** V1 protocol is `1.0`; manifests declare supported major plus min/max minor and required feature IDs. Major changes are incompatible. A minor extension may add optional fields/operations only without changing existing semantics; unknown required features reject before mount. Changes to reducers, precedence, stage contracts, serialization, or state policy require their own version updates and may require protocol major review. Old document compatibility is not a goal. No runtime silently falls back to Conservative, old combat phases, or a different ECS backend on mismatch.

### P-056
**Extension points.** Registered capability reducers, schemas, state owners, time policies within a selected temporal model, stage contracts, request ports, asset/presentation/input adapters, serializer migrations, and pure rule functions are supported V1 seams. Trusted extensions still obey memory lifetime, authority, stage access, finite derivation, and publication requirements. Arbitrary target-generating derivation, runtime code download, security sandboxing, universal engine/ECS adapters, cross-world atomic transactions, distributed consensus, and general speculative execution are deferred, not empty mandatory interfaces.

### P-057
**Conformance.** A conforming implementation implements all P-001 through P-060, the mandatory operation set, both propagation modes, and both temporal models. Contract suites use a managed model/oracle; real execution suites use Unity Entities worlds and standalone players. A mock-only implementation or successful compilation is insufficient. The [test catalogue](08-validation-and-performance.md) and [task registry](traceability.json) trace every requirement to executable acceptance work. Optional gameplay packages do not become kernel dependencies merely because fixtures use them.

### P-058
**V1 implementation profile.** C# plus Unity Entities is the only V1 ECS backend. Unity Jobs and Burst apply to eligible hot paths; managed composition remains outside Burst. IL2CPP and managed stripping are explicit build acceptance requirements with generated registration/serializer/generic-root coverage. An exact editor/package/native-toolchain baseline is specified in [Unity integration](04-unity-integration.md). Compatibility evidence must include official support constraints and a resolved package lock plus actual player execution; C# syntax or target framework compatibility alone does not pass the gate.

### P-059
**Genre validation before freeze.** The card, narrative, and real-time-action [reference compositions](07-reference-compositions.md) MUST pass without adding mandatory kernel gameplay schemas or phases. At least cards and narrative execute before provisional generic execution freeze; action and the cross-family composition execute before V1 conformance freeze. Each exercises automatic existing/future descendants, mount/unmount, reparent, mode changes, state retention, and ownership. A necessary example-specific rule belongs to its package; a general missing mechanism changes this protocol and its tests explicitly.

### P-060
**Evidence and release status.** The implementation records the exact build/catalog versions, resolved dependencies, native compiler, architecture, backend/stripping settings, test commands, logs, fixture hashes, and measurements. Budget numbers are provisional until measured on a named machine. Documentation validation does not imply Unity tests passed. V1 completion requires the dependency-ordered gates in the [implementation guide](09-implementation-guide.md), including failures/unload, IL2CPP, checkpoint recovery, and no per-frame scope traversal. Unknown product platforms/load targets remain explicit, not assumed team size or commercial requirements.

## 9. Visibility and common operation rules

This section applies to every §10 row. `C` means the serialized control lane, `B` a committed idle/end-step boundary, and `E` an execution stage. Public proposals are checked against the last published revision. Until `PublishPlan` succeeds, scope/configuration/mode queries and observers see the old committed assembly; operation status separately exposes staged progress. A mounted waiting instance is itself a published composition change. Private plan diagnostics can inspect staged data, but cannot be mistaken for world observation.

Every mutation uses P-050's ledger. Failures before live writes return `Rejected(code)` or `Cancelled`; failures after live writes return `Faulted(ApplyFault)` and follow P-031. An operation that published but cannot finish cleanup returns `PublishedWithCleanupErrors`, carrying the new epoch and retained resource IDs. Ordinary retry uses the same ID only to retrieve the same attempt, or a new ID for a fresh attempt. No operation permits unbounded retry. Read operations return immutable values or leased pages and have no mutation idempotency requirement.

For mutations: success emits an operation result and applicable composition/step/lifecycle event; rejection emits a diagnostic and retains the old visible revision; cancellation emits an operation result and no new epoch. Postconditions include releasing or tracking all staged resources. Each operation below supplies its additional pre/postconditions and a concrete conformance probe; the [validation catalogue](08-validation-and-performance.md) groups these probes into suites.

## 11. Protocol review against game families

The design-level [reference audit](07-reference-compositions.md) maps: card commands to demand-driven steps and one table owner; narrative facts to demand-driven state and chapter-derived bindings; real-time traversal to fixed steps and an optional motion adapter. None needs an ActorCoordinator, action phases, vitality, combat waves, physics phase, or animation phase in the kernel. A narrative-to-card reward crosses a typed command port, not a new universal effect bus. These are paper validations, not executed proof. P-059's executable gates remain mandatory before labeling this candidate stable.
