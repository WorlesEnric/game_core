# Decisions, research, and remaining validation

These decisions select the V1 implementation described by [Core Protocols](00-core-protocols.md). An unknown below is not an invitation to implement several competing backends. Each has a working default and an experiment that can invalidate it. Research date: **2026-09-25**.

## 1. Accepted architecture decisions

| Decision | Choice and rationale | Consequence / requirement |
|---|---|---|
| ADR-001: language/backend | C# and Unity Entities only. Concrete player/AOT evidence is more useful than a speculative ECS interface. | Unity query/scheduling code is intentionally engine-specific; [P-058](00-core-protocols.md#p-058). |
| ADR-002: composition model | Cordis-inspired managed scopes, declared services, resource lifetimes; ECS authoritative simulation. | No JS port, plugin-per-entity requirement, or security sandbox; [P-001](00-core-protocols.md#p-001), [P-003](00-core-protocols.md#p-003). |
| ADR-003: primary configuration | Automatic propagation is the world default; reusable compatibility is enough for eligible descendants. | Broader/emergent application is accepted; diagnostics and explicit exclusions/overrides remain available; [P-013](00-core-protocols.md#p-013). |
| ADR-004: one mode switch | Conservative changes the descendant grant predicate, not runtime architecture or memory safety. | Atomic full affected-closure mode transitions; services unchanged; [P-014](00-core-protocols.md#p-014). |
| ADR-005: conflict meaning | Contract-declared Additive/Replace/Ordered/Exclusive/Incompatible; only declared replacement uses rank by default. | Ambiguous exclusivity rejects intact rather than deleting a lower-ranked provider; [P-018](00-core-protocols.md#p-018), [P-019](00-core-protocols.md#p-019). |
| ADR-006: finite derivation | Static descriptors plus strictly lower-stratum inputs, finite outputs and hard planning bounds. | Expressive capability chains without recursive spawn/rule generation; [P-021](00-core-protocols.md#p-021). |
| ADR-007: change-driven control plane | Incremental indexes and cached recipe variants; full recomputation exists as a test oracle. | No per-frame tree walk, per-entity DI resolution, or duplicate state store; [P-023](00-core-protocols.md#p-023). |
| ADR-008: publication boundary | Prepare while old epoch runs; one world fence for assembly; nonthrowing final pointer/gate commit. | Atomic visible assembly, not storage transactions; postwrite failure halts; [P-030](00-core-protocols.md#p-030), [P-031](00-core-protocols.md#p-031). |
| ADR-009: state authority | Explicit owner grants and domain requests; direct owner writes are normal. | No universal coordinator or global command queue; [P-034](00-core-protocols.md#p-034), [P-042](00-core-protocols.md#p-042). |
| ADR-010: temporal models | CommandDriven and FixedStep at world creation; no implicit 60 Hz default. | Time policy is explicit; moving between models requires recreation in V1; [P-036](00-core-protocols.md#p-036). |
| ADR-011: execution graph | Plugin stage contracts plus per-system access/order, owner partitions and buffer edges. | Detect cycles/ambiguous overlap before activation; no mandatory physics/animation/combat phase; [P-039](00-core-protocols.md#p-039), [P-040](00-core-protocols.md#p-040). |
| ADR-012: state retention | Explicit RemoveDerived / PreserveDormant / TransferTo and registered migrations. | Unmount cannot silently erase progress or undo committed gameplay; [P-032](00-core-protocols.md#p-032). |
| ADR-013: recovery | Checkpoint to a fresh world after faults; no generic storage undo journal. | Runtime handles and callbacks never revive; external exactly-once delivery is a separate outbox/receiver concern; [P-049](00-core-protocols.md#p-049). |
| ADR-014: player extensibility | Mount/reconfigure precompiled registered plugins and declarative content at runtime. | Generated type/serializer/generic roots, IL2CPP/High stripping tests, no downloaded code; [P-009](00-core-protocols.md#p-009), [P-054](00-core-protocols.md#p-054). |
| ADR-015: integration timing | Early standalone risk probe, early automatic propagation slice, two families before provisional protocol freeze. | All three families, recovery, unload, replay and measured budgets required for V1 completion; [P-059](00-core-protocols.md#p-059), [P-060](00-core-protocols.md#p-060). |
| ADR-016: Unity failure dispatch | Guard direct generated system dispatch; do not use stock group's continue-after-exception loop. | A throwing-stage test must prove no downstream execution/publication; see [exact-source evidence](references/unity-evidence.md). |

## 2. Ranked unknowns and decisive defaults

“Fallback” means the smallest safe change if evidence invalidates the default. It never means silently weaken a confirmed requirement. No unsupported calendar estimate is provided. Complexity describes coupled engineering work, not a team productivity assumption.

| Rank / question | Default V1 decision | Smallest validating experiment and artifact | Fallback if invalidated | Complexity / uncertainty |
|---|---|---|---|---|
| P0: Does the exact selected toolchain resolve/build/run? | Unity 6000.0.75f1, Entities 1.4.6, Burst 1.8.28, Collections 2.6.6; macOS ARM64/Xcode 16.4 qualification target. | Clean UPM lock, generated registration, Burst job, runtime plugin mount, High-stripping IL2CPP executable log. | Review/update the complete compatible pin set and rerun; retain Entities/IL2CPP. Do not build Arch or call Editor success sufficient. | High coupling, unexecuted build risk. |
| P0: Can guarded system dispatch reliably enforce fail-stop? | Custom dispatcher uses exact package public managed/unmanaged update entry points and explicit fault latch. | Throw in managed stage after a write; fail ECB/snapshot path; assert zero later stage/commit and safe outstanding-job drain in player. | Fix/adapt dispatcher against pinned source, or review package patch; never rely on catching outside stock group. | Medium implementation, high correctness impact. |
| P0: Is derivation sufficiently expressive without target-generating closure? | 32 static strata with bounded same-target outputs; gameplay queues later spawns. | Existing/future card, gate and traversal targets plus a three-stratum cross-package chain; random differential oracle. | Add a justified declarative selector/reducer contract with tests; keep finite closure. Runtime recursive rule generation stays deferred. | Medium algorithmic uncertainty. |
| P0: Can preparation/apply preserve state within acceptable pauses? | Incremental closure and prepared resource/migration storage, whole-world assembly fence. | 100-target edit, 10,000-target mode switch, stale-prepared spawn, migrating owner slot while jobs run; record end-to-end and fenced duration. | Pause world for broad plan or explicitly raise budget; optimize indexes/layouts. Partitioned multi-epoch publication is not an unreviewed shortcut. | High coupling; product pause tolerance unknown. |
| P0: What shipping platforms must qualify? | A concrete macOS ARM64 baseline proves early risks, not product coverage. | Produce platform requirement list when product context exists; run identical minimal build probe on each required target. | Add platform-native CI/toolchains and adapter constraints; no claim of universal Unity platform support before evidence. | External requirement unknown, no assumed target market. |
| P1: How broad must live schema migration be? | Generated bounded migration paths for registered schema versions, explicit dormant state and owner transfer; arbitrary code hot reload excluded. | Numeric config change preserving state, v1→v2 field migration, failed migration retaining old epoch, checkpoint restoration. | Use explicit checkpoint/recreation for unsupported migration while keeping registered live migrations; never implicit reset. | Medium/high depending on domain schema. |
| P1: What is the real load shape? | Provisional synthetic fixtures, counts/latency/memory reported separately; no production capacity promise. | Record scopes, targets, contribution fan-out, request density, snapshot volume and locality from a representative composition. | Revise budgets from evidence and optimize measured hotspot. Preserve all eligible target effects; no silent drop. | Low measurement cost, unknown production demand. |
| P1: Does Unity physics/animation affect gameplay authority? | Primary action fixture is core-owned kinematic traversal; physics-owned Rigidbody mode is an optional explicit adapter. Presentation animation does not own game state. | One local PhysicsScene adapter scene and one animation output mapping; compare observation stamps/output under several render rates. | Keep physics observations as external inputs and document solver/replay limits. If animation must authoritatively drive rules, add a separate stage/authority contract with a real use case. | Medium adapter work, no general physics parity promise. |
| P1: Is snapshot/event retention adequate? | Bounded immutable pool, CursorExpired/resync and backpressure; durable reward outbox only where required. | Hold a slow reader while changing assembly and stepping; overflow event retention and retry outbox delivery. | Increase explicit capacity or reduce projection size; version a narrower snapshot schema. Do not expose live ECS memory to avoid copying. | Medium cost/latency tradeoff. |
| P2: Which asset backend is sufficient? | Generated asset keys + explicit Unity asset leases; add Addressables only for demonstrated asynchronous packaging needs. | Mount inactive precompiled content, unload one of several shared asset users, inject late load completion. | Pin/qualify an Addressables adapter and its dependencies; it does not change capability/lifecycle semantics. | Medium integration, isolated from kernel. |

The runtime should not freeze semantics before these early probes reveal contradictions. The documented defaults are still concrete enough to implement; a failed gate produces a focused protocol/adapter revision rather than an open menu of architectures.

## 3. Required V1 versus deferred work

Required V1 includes both modes, both temporal models, propagation/composition policies, incremental updates, runtime spawn recipes, reparenting, service dependency activation/retraction, state ownership, live migration for registered schemas, suspension/resume/unmount, bounded resources and callbacks, provenance, committed observation, checkpoint/restore, three distinct small game packages, a cross-family composition, generated AOT registration, player tests, and measured performance/failure evidence.

The following are excluded because they add large complexity to narrowly demanded features and are not needed to validate the confirmed scope:

- Another ECS/backend, C++ core, or universal engine abstraction: requires new query/lifetime/toolchain behavior without a V1 use case. Specifications and content remain reusable where meaningful.
- Untrusted plugin sandbox, downloaded runtime code, native code hot replacement: introduce process/security/AOT complexity beyond trusted precompiled mounting.
- Universal speculative execution, arbitrary gameplay undo, distributed/cross-world atomic transactions: require history, consensus or effect compensation beyond explicit domain owners and checkpoints.
- Cross-platform floating-point lockstep or rollback netcode: would require a separate product requirement and determinism model; recorded observation replay is provided now.
- Automatic conversion of Unity assets/physics/animation to Godot/Unreal: IDs and schemas do not make engine semantics portable.
- Workbench/editor panels, AI/chat interfaces, and AI workflows: explicitly outside the requested system, not hidden implementation waves.

The small size of reference games does not reduce the required framework contract surface. Every required mechanism remains traceable to [implementation tasks](09-implementation-guide.md) and [acceptance suites](08-validation-and-performance.md).
