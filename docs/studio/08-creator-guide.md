## A reviewed edit

1. Select the logical object or a location. Resolve overlap and scope first. Inspect the Context card for identity, residency and stale badges. Picking uses engine data; a screenshot is context, not the source of object identity. ([P2.1 §Verification](packets/P2.1-studio-ui.md), [SADR-007](02-architecture.md#8-decision-records-sadr--studio-adr-numbering-continues-after-the-kernels-adr-017))
2. Enter a specific prompt and press **Send**. For example, the recorded live demonstration selected the Village Well and requested “Move this well one metre to the east”. The returned move candidate was staged and then rejected. That evidence does not establish every proposed gameplay workflow. ([P2.1 §Evidence](packets/P2.1-studio-ui.md#evidence-artifactsstudioevidencep21readmemd))
3. Follow the task in **Tasks**. `queued`, `starting`, `running`, `waiting`, `done`, `failed`, `cancelled` and `unknown` are etos task statuses; candidate/import status is separate. Unknown is displayed as Unresolved, never success. Answer a clarification or cancel explicitly. ([ETOS §3](04-etos-integration.md#3-task-lifecycle-mapping), [P2.1 §Reconciliation](packets/P2.1-studio-ui.md#reconciliation-with-p22-what-changed))
4. Open the candidate. The default etos gateway imports and stages candidates on arrival; the UI adopts that stage. Otherwise choose **Preview**. Check operations, target scope, requirements, diagnostics, retained artifacts and **Compare** / **Show after**. A move preview uses a ghost. ([P2.1 §Reconciliation and Verification](packets/P2.1-studio-ui.md))
5. Resolve a `Conflict` with **Rebase**, which re-plans against current stamps, or **Skip** the affected operation. A destroyed or unloaded target is `StaleTarget`, not a stamp conflict. Review again after rebasing. ([Authoring §7 and §9](03-authoring-contracts.md), [P1.6 §Decisions](packets/P1.6-studio-core-unity.md#decisions))
6. Choose **Apply** or **Reject**. AllOrNothing rolls back an apply failure; BestEffort records which operations applied or failed. Reject reasons are recorded locally in the journal/log; the companion has no reject-reason route, as a local decision. Save authored assets/scenes separately. ([P1.6 §Decisions](packets/P1.6-studio-core-unity.md#decisions), [P2.2 decision 9](packets/P2.2-studio-etos-client.md#decisions-and-deviations))
7. Review **History**, including task links and any GameCore operation ids. Undo/redo uses inverses and retained artifacts; it does not generate the asset again. A new apply clears the redo stack. ([P1.6 §Decisions](packets/P1.6-studio-core-unity.md#decisions))

### NPC and dialogue authoring boundary

For placement, make the intended region scene active, select an existing NpcDefinition in Context and run **npc.addAt** with `location` in metres, optional `yaw` in degrees and `name`. The definition must reference an entity definition, and the location must lie inside the active scene's region. Use **npc.setPatrol** on that definition for world-space patrol points and wait time. Use `npc.setDialogue` to assign a typed graph; P1.7b added that tool. ([NpcTools.cs](../../Packages/com.gamecore.gameplay.npc/Editor/NpcTools.cs), [P1.3 NPC tools](packets/P1.3-player-npc-interaction.md#npc-comgamecoregameplaynpc))

The existing-definition walkthrough qualified by P4.2d is:

1. Open the boot scene and Studio. In Edit Mode, make the intended region scene active and select the existing **Maren** NPC definition in Context. It already references an entity definition and dialogue graph.
2. Run **npc.addAt** with a position inside that region, optional yaw and a name. Check the new placement in Context and History.
3. Open **Dialogue**, select Maren's bound graph and a terminal line. Use **Add line**, enter text and review the journaled change. Keep the graph reachable; altering its entry can disconnect earlier nodes.
4. Save. Use normal History Undo for the dialogue edit and placement. P4.2d's test restored the 20-entity / 13-node baseline. This exercise reuses a definition; it does not create a unique NPC definition or prove the generated ferryman navigation workflow.

The old authoringId and nested-list inverse blockers are fixed. The generated ferryman candidate in W-AI-02 still failed `GP-DLG-005` at bake because it disconnected nodes 0–7. Keep that candidate as failure evidence rather than editing its bytes. ([P4.2d §R2 fixes and R5 qualification](packets/P4.2d-live-rerun.md#r2-fixes-and-r5-qualification), [P1.6 follow-up](packets/P1.6-studio-core-unity.md), [P1.7b §1](packets/P1.7b-gameplay-hardening-metadata.md#1-what-was-built))

## Voice and generated assets

Voice needs a paired app, a ready companion, a `studio-voice` realtime provider and an available microphone. Capture is converted to PCM16 mono 24 kHz. The transcript shows partial revisions while listening; only a final user transcript enters the prompt. Read it, correct it and press **Send**; reviewing the eventual candidate and pressing Apply is another separate action. Product voice setup errors are surfaced without automatic session retries. The live microphone evidence used a PipeWire virtual source, so it is not a recording of a creator speaking into a physical microphone. ([P2.2 §Verified and decision 12](packets/P2.2-studio-etos-client.md), [PromptBar.cs](../../Packages/com.gamecore.studio.ui/Editor/Prompt/PromptBar.cs))

Image generation and TTS return artifacts through the companion. The client checks sha256 and byte count before retaining bytes; imports go through journaled `asset.import`. `asset.generate` produces an import candidate. `EtosMediaGenerator` provides image and speech adapters; generation is not proof that a material or dialogue voice binding has been changed. Review the candidate's assignment operations as well as the imported file. ([P2.2 §Built, Verified and API](packets/P2.2-studio-etos-client.md), [Authoring §6](03-authoring-contracts.md#6-change-set-owner-studiocore-edit))

3D generation is **blocked: no provider credential**. Sound-effect generation also returns `not_configured`; procedural Hollowmere sounds do not prove live SFX generation. `dialogue.generateVoice` and audio generation tools have different current tier/gateway wiring, so consult their diagnostic rather than assuming a provider chip makes every tool available. ([SADR-020](02-architecture.md#8-decision-records-sadr--studio-adr-numbering-continues-after-the-kernels-adr-017), [P1.4 decisions](packets/P1.4-dialogue-quest-logic-inventory.md#decisions-where-05-was-silent), [P1.5 decision 10](packets/P1.5-ui-audio.md#decisions-where-05-was-silent), [P2.2 §API](packets/P2.2-studio-etos-client.md#api))

## Mechanisms: Stage, verdict, Admit, undo

A mechanism candidate carries a package and proposal. Choose **Stage**; local CLI JSON and **Record verdict** files cannot authorize code. The client fetches a signed passing record through the authenticated companion and verifies it there. Then explicitly choose **Admit**. All seven gates must pass, with exact source/catalog/package/proposal bindings. ([R2-B](packets/R2-B-admission.md), [04 §6](04-etos-integration.md#6-staging-code-admission))

In Play, the game's admission binding captures/stops, recompiles, restores and polls trusted smoke before success. Missing services leave a recoverable pending record. P4.2d's real run passed stage in 158.122 s but stalled in compile and rolled back with `catalog_mismatch`; restoration/smoke/undo were not reached. The warm stage limit remains 360 s and admission target 90 s. ([P4.2d §Stage and admission](packets/P4.2d-live-rerun.md#stage-and-admission), [09 §GameBoot admission binding](09-plugin-developer-guide.md#gameboot-admission-binding))

## Game saves and settings

Hollowmere currently starts at its main menu; **New Game** opens the HUD. Its save/load screens exist, but production saves are **unavailable (`GP-UI-014`)** until game checkpoint codecs, `UseSaves` and complete restored-session wiring arrive. The successful UI save test used test codecs and does not establish working production Hollowmere saves. ([P1.5 §GameBoot, Verification and Open](packets/P1.5-ui-audio.md))

For a game with SaveService installed, slots are `<slot>.gcc` plus `<slot>.json` under `Application.persistentDataPath/saves`. Loading validates the pair, catalog, recipe revisions and slot migrations before replacing the world. Keep the two files together. A recipe revision change can refuse an old save even when slot migrations exist. ([P1.2 §1.4 and §3](packets/P1.2-save-restore.md), [save runbook §7](../operator/checkpoint-and-recovery.md#7-production-restore-and-saves))

Open **Project Settings → GameCore Studio → ETOS**. Set **App key file**, optionally **Node URL**, **Max cost per op (USD)**, **Stage candidates on arrival** and **Generated assets folder**; choose **Save and restart session**, then **Test connection**. **Open node UI** uses `http://127.0.0.1:7400` by default. Settings store the key path, never the credential. `GAMECORE_ETOS_KEY_FILE` overrides the path. The default media ceiling is USD 0.50, but P0.1 reports no configured prices, so USD budgets do not bind; do not treat the field as a proven spending cap. ([EtosSettingsProvider.cs](../../Packages/com.gamecore.studio.etos/Editor/EtosSettingsProvider.cs), [P2.2 §Built and decision 2](packets/P2.2-studio-etos-client.md), [P0.1 §4](packets/P0.1-host-etos.md))
