**How this differs from the coordinator's wording, and why:** `POST /tasks` still answers with the outcome of the
start (`running`, `queued` or `failed`) when the caller waits. The start is not handed to a separate scheduler with
an immediate `starting` answer. What changed is that the work runs on a node-owned task, so dropping the request no
longer stops it, and the request→task row is always written. I kept the answer because the etos API documents it
(`open` "returns the record as it is afterwards") and because existing tests and the SDK rely on it. Two things
make a repeat during an open safe:
- the request record is posted under the request id (`op = task:<id>`, an idempotent publish), so a repeat gets the
  same position;
- the node derives the task id from worker, topic and position, and waits on the per-id open lock.

So a repeat cannot open a second task.
