## 2. The three findings that matter

### 2.1 One genuinely unreachable required clause: P-012's unexpected-provider failure → **Blocked**

P-012 says: *"An existing provider that fails unexpectedly cannot be kept active: the world stops admission and
faults if a safe dependency-closure deactivation cannot publish."*

The audit found that V1 has **no path that fails an already-Active provider**:

* `Packages/com.gamecore.composition/Runtime/Lifecycle/InstallationStateMachine.cs` — the only `Failed` edge is
  `Preparing → Failed`. There is no `Active → Failed`.
* `Packages/com.gamecore.composition/Runtime/Lifecycle/ActivationLedger.cs` — the only failing transition is
  `AbortCandidate` ("a candidate can only fail from Preparing"). No method fails a live activation.
* No composition-side caller signals the world's fault latch. `UnityWorldHost.EnterFaulted` /
  `UnityExecutionDriver.Fault` exist and `WorldCompositionBridge.SubmitAndExecute` does refuse a non-`Running`
  world, but nothing connects "a dependency-closure deactivation cannot publish" to that latch.

So the row is **`Blocked`**, with the missing mechanism named in the index itself. It is *not* marked Pass, and the
reachable half — a blocked deactivation retaining its resources and never reporting `Disposed` — is evidenced
separately (`TeardownAndQuarantineTests.ABlockedJobPreventsTheBufferReleaseUntilTheJobCompletes`,
`ResourceGateTests.UnmountPublishesCleanupErrorsWithRetainedReferences`, `LifecycleFaultTests.AJobHeldInFlight...`).

**This is a mechanism change, not a Wave 8 fix.** Adding an `Active → Failed` edge plus a composition-to-world
fault signal during the conformance freeze would invalidate the W1..W7 gates and contradict Wave 8's role. The
honest outcome is a `Blocked` row that stops GC-030 from recording V1-complete, exactly as the Wave 8 gate's
"No NotRun or Blocked required case is waived" requires. §6 proposes it as the one open required-V1 item.

### 2.2 One contradiction inside 00, resolved in 00

P-037 ended with *"Terminally invalid inputs finish as `Rejected` without an empty CommandDriven step"*, while
P-047 says *"Accepted but unexecuted commands to a suspended/removed route finish `Cancelled(RouteRetired)`"*. Under
a literal reading of P-037 a retired route is also "terminally invalid", so the two sentences contradicted each
other, and the shipped code (`BoundedBufferRules.CarryNextStep`) emits `Cancelled` + `DiagnosticCode.Cancelled` for
a carried row whose target is gone, citing P-047.

Resolution: P-037's sentence now distinguishes the two outcomes explicitly — revalidation-invalid input is
`Rejected`; an accepted-but-unexecuted command on a suspended/removed route is `Cancelled(RouteRetired)` under
P-047, "and the two outcomes are distinct rather than interchangeable". Both halves are asserted by existing tests
(`RequestLedgerTests.UnknownAndRetiredRoutesAndSchemaMismatchesAreRefused`,
`BoundedMessageBufferTests.AnUnconsumedNextStepQueueCarriesForwardWithTerminalCancellations`). No implementation
changed. The documentation validator passes after the edit.

### 2.3 Two clauses and one operation whose strongest evidence is new

* **P-043** "duplicate producers are legal when registered; fan-out uses explicit immutable read ports" — no test
  declared two producers of one buffer, none declared a read port, and no test closed a stage cycle through a
  buffer edge.
* **P-052** "the required codes include …" — nothing asserted that `DiagnosticCodeText.Values` holds exactly the
  twenty names 00 lists, in that order, each round-tripping through the text mapping.
* **P-007** "service bindings resolve once per assembly, not per target per frame" — no binding-resolution counter
  exists. The clause is judged **Pass** on the counter that does exist
  (`TelemetryBuildSwitchTests.ServiceStringLookupsAreCountedWhereResolutionHappensAndNowhereElse` asserts zero
  string service resolutions in every frame of a 10,000-step replay, and the counter is placed at the one
  string-keyed resolution in production), plus new lease-identity assertions.

## 5. Requirement / operation → evidence coverage mapping

`artifacts/conformance/evidence-index.json` is the mapping, and it is the deliverable: for every row it lists each
clause, the evidence reference, the resolved result file and the derived status. This section states how the map is
built so a reviewer can falsify it:

* **`dotnet:<FQN>`** resolves against every TRX under `<root>/trx/`. Any recorded `Failed` outcome makes the
  reference `Fail`, even if another run passed.
* **`unity:<FQN>`** resolves against every NUnit3 XML under `<root>/unity/` (EditMode and PlayMode).
* **`probe:<Mode>/<name>`** resolves against every `probe-*.json` under the tree, matched by the document's own
  `mode`. A qualified recorded name (`narrative/gc027-...`) also answers the bare form.
* **`check:<key>`** reads an archived document by path and asserts a specific field or marker line
  (`clean == true`, `verdict == pass`, a log line that only a passing check prints, …). A missing document is
  `NotRun`; a document whose value disagrees is `Fail`.
* A clause's status is the worst status of its evidence; a row's status is the worst of its clauses. A `blocked=` /
  `deferred=` marker overrides a `Pass`, so a documented gap cannot be silently outvoted by weaker evidence.

Suite-level coverage is `artifacts/conformance/suite-status-w7-gate.json` (24/24 Pass on the W7 corpus), and the
required-suite list for each operation is recorded in the index's operation rows (`required_suites`), taken from
08's "Operation-to-suite coverage" table.

   (`OwnerAuthorityValidator`) has no transfer input, so a cross-owner writer overlap always rejects; the only

   that note recorded in the clause, because the normative sentence is a permission that qualifies the rejection
   obligation, and the rejection obligation is fully evidenced.
6. **The compatibility report's `Source revision`** is `git rev-parse HEAD` of the tree the tool runs in. On the
   build host that will be the GC-028 revision once committed; the value in the shipped document is the

7. **Assumptions about the fresh run.** The index and compatibility report are shipped built from

   `artifacts/conformance/results/` and regenerates both from it, so the two `NotRun` requirement rows and the 14
   `pending` references to this task's new tests resolve there.
8. **Doc ambiguity resolved by picking the 00-consistent reading** (per the brief): P-037 vs P-047 (§2.2). Also,

   a world whose step is in flight.

### 9.3 What a passing run proves, and what it does not

* A `Pass` in `suite-status.json`, `evidence-index.json` or `compatibility.json` means the referenced result file
  reported it. Nothing in this task's tooling asserts a status on its own.
* The index resolves against whatever `--evidence-root` names; regenerating it from a fresh tree is the intended
  workflow, and `--check` is what makes a stale or incomplete tree fail rather than publish.
* `P-012` stays `Blocked` and `P-060`'s timing clause stays `Deferred` no matter how many times the matrix runs —
  they are properties of the implementation and of the owner decision, not of the run.
