## What this artifact is

A complete inventory of the GameCore V1 required surface: all 60 normative requirements `P-001`..`P-060`
(`docs/game-core/00-core-protocols.md`) and all 26 catalogued operations `O-01`..`O-26` (§10 of the same
document, with required suites and distinguishing probes from the `Operation-to-suite coverage` table in
`docs/game-core/08-validation-and-performance.md`). Owner tasks come from `docs/game-core/traceability.json`
(cross-checked against the `### GC-0NN` sections of `docs/game-core/09-implementation-guide.md`; no disagreement).

6/6 PlayMode, and all ten player probe scripts at five runs each (GC-001 includes an expected-negative case).

## How a status was assigned

`status` is exactly one of three strings, and every row uses one of them. Quoted rules (GC-012 brief):

> - Status vocabulary is EXACTLY these four strings: `Implemented+Evidenced`, `Partial`, `Not yet`,
>   `Evidenced-Elsewhere` is NOT allowed — use only the first three.
>   - `Implemented+Evidenced` = an implementation exists AND an archived executable artifact on the Linux build host
>     exists for it (look in `artifacts/*/BUILD_REPORT.md`, `artifacts/*/HANDOFF.md`, `artifacts/*/toolchain/*.json`,
>     `artifacts/*/unity/*.xml`, `artifacts/*/trx/`).
>   - `Partial` = implemented or partly implemented, but the evidence does not cover the whole requirement, or the
>     archived evidence is from an earlier wave only.
>   - `Not yet` = no implementation/evidence yet.
> - O-01..O-26 are only `Implemented+Evidenced` if BOTH an implementation exists in `Packages/` and an archived
>   executable artifact on the build host covers that operation's distinguishing probe. Reviewers will check that you
>   did not over-claim. When unsure between `Partial` and `Not yet`, prefer `Partial` only if some code path exists;
>   otherwise `Not yet`.
> - Requirements that are semantic/kernel-wide (e.g. P-001, P-057, P-059) are `Partial` until their owning later
>   tasks (waves 5-9) close them; say which.
> - Never mark anything `Implemented+Evidenced` on the strength of a document that itself says the result is
>   `NotRun (pending orchestrator build host)`.

How the rules were applied here:

1. **Current evidence.** The W4-GATE run holds 750/750 .NET, 781/781 EditMode, 6/6 PlayMode and ten player probe scripts × five repetitions. GC-012's earlier 655/655, 613/613 and nine-mode run remains separately archived; the current run repeats its probes and adds GC-013 and W4-GATE coverage.
2. **Requirements.** A `P` row is `Implemented+Evidenced` only when the mechanism exists in `Packages/` **and** the
   current executable evidence directly exercises the requirement's normative content with no named sub-clause
   left unexercised. If any sub-clause maps to a later wave's named mechanism (checkpointing, adapters, retention
   under limits, replay, measured budgets, the action family, cross-family composition), the row is `Partial` and the
   `gap` names that sub-clause. At the time of this assignment only `P-053` was `Not yet`, because no checkpoint
   code existed anywhere in the tree; GC-018 later supplied it and the row is now `Implemented+Evidenced`.
3. **Operations.** An `O` row is `Implemented+Evidenced` only when a handler exists in `Packages/` **and** the
   archived artifacts cover the operation's *distinguishing probe* from the `Operation-to-suite coverage` table —
   not merely its happy path. `O-20`..`O-22` were `Not yet` at the time of this assignment: `grep` over `Packages/` found no `Checkpoint`,
   `RestoreCheckpoint` or `RecoverWorld` code path. GC-018 later added the capture and restore paths, so `O-20` and
   `O-21` are now `Implemented+Evidenced` while `O-22` (which that task explicitly did not compose) stays `Not yet`. `O-24` is `Partial` because a code path exists (the callback gate) but the host side of the
   operation does not.
4. **`ownerTasks`.** For requirements, the tasks in `traceability.json` whose `requirements[]` carry the id. For
   operations, the union of the tasks owning the required suites listed for that operation, mapped through
   `tasks[].tests[]`. Both sets are listed in wave order.
5. **`nextOwner`.** The lowest-wave task in `ownerTasks` whose contract covers the missing mechanism named in `gap`
   (ties broken by wave); it is always a task in `ownerTasks`. Where the closing mechanism belongs to a task outside
   `ownerTasks`, the `gap` sentence names that task explicitly (for example `P-050`'s restore reservation is
   `GC-018`'s work while the row's `nextOwner` is `GC-014`). Kernel-wide rows (`P-001`, `P-057`, `P-059`, `P-060`)
   name the later-wave task that closes them.
6. **Evidence paths.** Added W4-GATE artifacts are archived under `artifacts/w4-gate/`; earlier GC-012 and W3 paths remain cited for their separate runs. No authoring-host `HANDOFF.md` is cited as a passing result.
